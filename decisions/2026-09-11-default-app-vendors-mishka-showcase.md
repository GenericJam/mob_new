# The default generated app vendors the Mishka Chelekom showcase

- Date: 2026-09-11
- Status: accepted
- Issue: MOB-188

## Context

The default native app `mix mob.new` produced was a landing page of nav
buttons and two rows of theme tabs. The Mishka Chelekom project ported its
component kit to Mob as a real Mob app (`development/mob` in the
mishka_chelekom monorepo, itself generated by `mix mob.new` around mob_new
0.4.20): 77 native composites, a gallery that presents each one with live
examples, and a compact icon theme bar. We want a fresh app to look like
that gallery, with credit and a link to https://mishka.tools/chelekom.

Three ways to get the code into a generated project were weighed:

1. **Depend on `mishka_chelekom` and run its `mix mishka.ui.gen.mob.components`
   at generation time.** The published package (0.0.10-alpha.6) ships the
   mob mix tasks but its `priv/mob` template directory is excluded from the
   Hex `files:` list, so the generator has nothing to render; there is no
   generator for the showcase (gallery, kit, per-component pages) at all; and
   the dependency would pull igniter, spark, plug and friends into every
   mobile project's dev deps.
2. **Publish the showcase as a Mob plugin package** (tier-2/3 manifest with
   `expand:` composites and screens). Architecturally the cleanest, but it
   needs a package owner and an agreement with the Mishka maintainers before
   mob_new can depend on it, and it does not exist yet.
3. **Vendor the Mishka app's sources into mob_new's templates**, the way
   Mishka's own `mix mishka.mob.sync` derives its consumer templates from the
   same app.

## Decision

Vendor (3), through `mix mob_new.sync_mishka PATH`. The task copies the
components, showcase, theme bar and showcase test from a Mishka checkout,
rewrites `MishkaMob` / `mishka_mob` to the template assigns, clears the
target directories first so upstream removals propagate, regenerates the
fenced `config :mob, :extra_tags` block from the catalog, and records the
upstream commit in `priv/mishka_sync.txt`. The home screen, `app.ex` and the
home-screen test are hand-maintained because they carry the generated app's
own name, logo, credit footer and `--blank` gating.

Only the home-screen and showcase-registry tests ship in a generated app; the
per-component unit tests and the Android instrumentation tests stay upstream
where the components are maintained.

`--blank` skips the whole vendored tree and keeps the previous Light / Dark
home screen, so a minimal app is still minimal. LiveView projects are
untouched (`liveview_phoenix_owned?/3` already blocks `lib/<app>/` and
`test/`).

## Consequences

- The archive grows by about 1.7 MB of Elixir source (roughly 500 KB
  compressed). Every non-blank generated app carries 140 extra files that
  most users will never edit; that is the trade for a first screen that
  demonstrates a real component library.
- Keeping up with Mishka is a manual re-sync plus a regenerate-and-test pass,
  not automatic. `priv/mishka_sync.txt` says which commit the templates came
  from.
- The Mishka app's composite tags need the `~MOB` sigil to accept them
  without rewriting `deps/mob/priv/tags` (the hack the Mishka app itself
  uses). mob PR #161 (same issue) adds `config :mob, :extra_tags` for that;
  until a mob release carries it, a generated app compiles with one warning
  per Mishka tag use.
- Every card preview is composite-expanded inside the home screen's list
  renderer. `Mob.Screen` runs the composite pass before the list pass, so a
  preview emitted from a `:list` row would otherwise reach native as an
  unknown node (the Avatar, Rolling Number and Separator cards rendered
  blank on iOS before this).
- The popover-family components emit an `:anchored` node that the Mishka app
  renders with roughly a thousand lines of additions to its own Android
  bridge, and that mob's iOS renderer does not have at all. Until those land
  (native parity, same issue) the generated `showcase_test.exs` reports the
  gap and those components fall back to inline panels on device. Publishing
  mob_new with this default app is gated on that parity work.
- If Mishka later ships its `priv/mob` templates and a showcase generator in
  Hex, option (1) becomes viable and the sync task can be retired in favour
  of running their generator; nothing here precludes that.
